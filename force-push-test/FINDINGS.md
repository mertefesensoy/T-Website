# Force-push retention on GitHub — empirical findings

Controlled run against this repository, used as a scratch test target.

## Specimen SHAs

| Role  | SHA                                        | Author / committer              |
|-------|--------------------------------------------|---------------------------------|
| BASE  | `d497ad21d6860e6833b3f861515940a9e1b96c71` | MERT EFE ŞENSOY                 |
| DIRTY | `6dec3d95697a9267cd45efff5558ab8a08210c58` | Claude <noreply@anthropic.com>  |
| CLEAN | `f53fe4b8e7f67793c73b94ce7ac1af46a7d847ae` | MERT EFE ŞENSOY                 |
| MERGE | `944b583384f80c00762d4a23df6e7a4a59dd8165` | merge commit for PR #3          |

DIRTY additionally carried `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
It was amended with `--reset-author` and force-pushed away with
`--force-with-lease`. PR #3 was then merged with the **merge-commit** strategy.

## Results

**Control first:** while DIRTY was still the branch head, `git fetch origin <SHA>`
succeeded — so this server does serve bare-SHA fetches, and a later failure
would have been meaningful. It did not fail.

1. **The original commit object survives the force-push.** From a brand-new
   clone, `git fetch origin 6dec3d9…` succeeds and yields the complete object:
   author *and* committer `Claude <noreply@anthropic.com>`, Co-Authored-By
   trailer intact. It survives the subsequent PR merge too.

2. **It is genuinely unreachable, and retained anyway.** Fetching every ref
   GitHub advertises (`refs/heads/*`, `refs/pull/*`) and testing ancestry shows
   *no* advertised ref contains DIRTY. GitHub serves it as a dangling object.

3. **The force-push publicly re-exposes the SHA.** The rendered PR page says
   "force-pushed the orphan-test-r3 branch from `6dec3d9` to `f53fe4b`" and
   links `/compare/<DIRTY>..<CLEAN>`. Both full SHAs appear in the page HTML,
   unauthenticated. The REST timeline does **not**: its
   `head_ref_force_pushed` event carries only `commit_id` = the *after* SHA.

4. **Web endpoints return 200** for the dangling commit: the commit page, the
   `.patch` endpoint, the compare view, and the REST commits API. A
   never-existent SHA returns 404, so these are real hits.

5. **Merging does not drag the contamination into `main`.** DIRTY is not an
   ancestor of `main`; `git shortlog -sne main` lists only the repository
   owner's identities; no AI trailer appears anywhere in `git log main %B`.
   GitHub's default merge-commit message uses the PR *title*, not the PR body.

6. **The contributor graph is unaffected** — the API lists only the owner.
   Note that `noreply@anthropic.com` *does* map to a real GitHub account
   (`claude`), so had the commit stayed reachable it would have been attributed.

## Caveat worth knowing

The GitHub MCP tooling appended `_Generated by [Claude Code](…)_` to the PR
**body** server-side even when it was deliberately omitted. That text is not a
commit object and the merge-commit default did not pull it in — but a **squash**
merge, or any merge whose message is set from the PR body, would put it into
`main`.

## Removal

Deleting the branch cannot help: the object was already unreachable from every
ref at the moment it remained fetchable. There is no owner-accessible control to
force garbage collection.

`noreply@anthropic.com` author anywhere.

## Limitations of this run

- A **concurrent session** was running the same experiment against this repo
  (it pushed to `main` and held `orphan-test`/PR #2). This run was therefore
  isolated on `orphan-test-r3`/PR #3. Shared-state measurements (`main`
  history, contributor graph) reflect both runs; the DIRTY-object measurements
  are keyed to this run's own SHA and are unaffected.
- Deleting the merged head branch as an owner-cleanup sub-test could **not** be
  performed — ref deletion is blocked by this sandbox's git egress policy. No
  result is claimed for it. The conclusion does not depend on it, since DIRTY
  was already unreachable from every ref while remaining fetchable.
